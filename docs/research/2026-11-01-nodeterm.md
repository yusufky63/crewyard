## What it is

- **Canvas.** A node-based terminal manager. Terminals and agent CLIs (Claude Code, Codex, Gemini, opencode, Copilot, Cursor, Grok, Antigravity) are draggable nodes on a pan/zoom canvas (React Flow). The canvas also holds sticky notes, Monaco editors, diffs and web nodes.
- **Board.** Every project is also a kanban board whose cards are live sessions.
- **Persistence.** Sessions persist through tmux on macOS and Linux, and through a standalone session-host process on Windows.
- **Agent status.** It comes from agent hooks, not from screen scraping.
- **Other features.** Source control panel, GitHub Issues on the board, phone pairing over an E2E relay, local Whisper dictation, and auto-update through electron-updater.

## How it differs from Crewyard

| | nodeterm | Crewyard |
|---|---|---|
| Model | A multiplexer: you start and drive each agent | An orchestrator: a crew is proposed, you approve, a deterministic scheduler runs it |
| Agent powers | Agents drive the canvas through a CLI: open nodes, spawn teams, read each other's transcripts | A run cannot create runs (PLAN.md §2, §9.1); this is a safety rule, not a gap |
| Git | Commit, push, sync and publish from a VS Code-style panel | Agents commit in their worktree; push, PR and merge always wait for your click |
| Spend | No budget layer in the README | Caps, spend provenance, daily limits, admission control |

## Ideas worth taking later

Each idea below names the nodeterm doc it comes from, what we have today, and the size of the change under AGENTS.md's tiers.

### 1. Sessions that outlive the app on Windows

- **Source:** `docs/windows-session-host.md`.
- **How it works:**
  - A detached, long-lived Node process owns the real PTYs (node-pty) and keeps a headless terminal emulator per session (`@xterm/headless` and `@xterm/addon-serialize`).
  - That way it can answer "what does the screen look like now" after the app reattaches.
  - It speaks newline-delimited JSON over a local named pipe or Unix socket.
  - Closing or crashing the app no longer kills running terminals and agent CLIs.
- **What we have:**
  - Agents are children of the daemon and are killed as a tree on stop (PLAN.md §4).
  - On restart, recovery marks gone runs `interrupted` and offers native resume.
  - The Terminal tab's shells die with the app.
- **When:**
  - For the Terminal tab it is a Medium change.
  - For agent runs it would change a PLAN.md §3 decision (process ownership), so it is Large and needs an ADR.
  - The ADR must keep tree kill on stop, the daemon's ownership of every process, and no TCP listener.

### 2. Deterministic approvals for Claude Code sessions started outside the app

- **Source:** `docs/hook-reply-approvals.md`.
- **How it works:**
  - The `PermissionRequest` hook writes the request to a private file and waits.
  - Its stdout decision (`{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`) is the answer, so nothing types keys into a terminal.
  - On timeout it prints nothing and Claude shows its own prompt, so it fails open to the normal dialog.
  - On the main thread the hook runs concurrently with Claude's dialog and the first answer wins. For a subagent's request the dialog waits for the hook.
  - A longer wait is used for `ExitPlanMode` and `AskUserQuestion`.
- **What we have:**
  - Runs started by Crewyard already answer approvals through each adapter's structured protocol.
  - PLAN.md §4 "Ingress" lists Claude Code hooks for sessions you started outside the app. Only the report server is built.
- **When:** with the external ingress, which the Crewyard MCP server session (ADR 0021) is building. A reply through our per-user pipe would replace the file. It is Medium on top of that work.

### 3. Ask before writing into an agent's global configuration

- **Source:** `docs/agent-integration-consent.md`.
- **How it works:**
  - Per agent and per SSH host, the choice is `enabled`, `declined` or not asked.
  - Declining removes exactly what the app wrote: hook entries by exact command, skill files by an exact-content receipt. A file the user edited is kept and listed.
  - Their own lesson: injected instructions took 17,102 bytes of Codex's 32 KiB `project_doc_max_bytes`, crowding out the repository's own instructions.
- **What we have:** each run gets its configuration through the runner's own config dir and child environment (PLAN.md §6, ADR 0007).
- **Check to run later:** confirm that no adapter writes to `~/.claude`, `~/.codex`, `~/.gemini` or `~/.config/opencode` outside a per-run or per-profile folder. Measure how many bytes of a runner's instruction budget our injected text takes.
- **When:** Small (an audit and a test). Medium if a consent setting is needed.

### 4. Memory per session

- **Source:** `docs/session-memory.md`.
- **Measured there (95 Claude processes on a 64 GB host):**
  - one `claude` process: average 335 MB, peak 1,159 MB;
  - MCP children: 30 to 200 MB more each (Playwright MCP with Chrome about 200 MB);
  - one Claude tree: 440 MB to 1.2 GB;
  - the memory is the CLI's own V8 heap, not the manager's.
- **What we have:** total RAM in the status bar and a 1 GB free-memory floor in admission (D7).
- **Idea:** a per-run memory breakdown (process tree RSS, MCP children included) in the status bar's RAM item. It answers "why does my next task wait".
- **When:** Medium. The numbers above are a starting point for the per-run estimate admission uses.

### 5. Distribution details

- **Source:** the README and `.github/workflows/download-badge.yml`.
- **Details:**
  - The macOS cask is in the official `homebrew/cask`, so no tap is needed.
  - Linux ships `.rpm` beside the AppImage and `.deb`. The AppImage needs FUSE 2, which Fedora lacks by default (`fuse-libs`).
  - Windows ships a portable zip beside the installer.
  - The download badge counts only installer files, because GitHub's total reads about 14 times higher once updater traffic (`latest-*.yml` polls, deltas, blockmaps) is counted.
- **When:** if the website shows a download count, count installer assets only. Homebrew and `.rpm` are Small additions to the release pipeline once the macOS and Linux builds have run for real.
